# DB-STD-004 — قرارداد انتخاب نوع ورودی و پذیرش فرانت‌اند

**تاریخ:** 2026-11-19  
**وضعیت:** DONE — قرارداد منطقی انتخاب ورودی و admission فرانت‌اند تثبیت شد؛ پیاده‌سازی UI و اتصال به سرویس‌ها خارج از دامنهٔ این Task است.  
**مرجع پیشرفت:** `database/DATABASE_CONFIGURATION_MASTER_WORKING_PACKET.md`، Task 024.  
**مبنای تصمیم:** Master Packet §§3.6، 3.7، 3.12 و 3.13؛ تصمیم‌های مصوب مالک دربارهٔ Excel برای CODAL، دو خانوادهٔ گزارش، ورودی‌های مستقل بازار/FX و fail-closed.

## 1. هدف و مرز مسئولیت

این قرارداد تعیین می‌کند کاربر پیش از ارسال ورودی چه نوع داده‌ای را انتخاب می‌کند، چه اطلاعات زمینه‌ای باید مشخص باشد و سیستم چگونه سازگاری فایل را با استاندارد انتخاب‌شده بررسی می‌کند.

- کاربر نوع ورودی موردنظر را صریحاً انتخاب می‌کند.
- انتخاب کاربر صرفاً اعلام قصد است و به‌تنهایی اثبات نمی‌کند فایل با آن نوع سازگار است.
- سیستم فقط استاندارد فعال و نسخه‌دار همان نوع ورودی را اجرا می‌کند.
- سیستم حق ندارد نوع انتخاب‌شده را با حدس، تشخیص خودکار عمومی یا fallback به نوع دیگری تغییر دهد.
- اگر استاندارد معتبر/فعال برای نوع انتخاب‌شده وجود نداشته باشد، آن گزینه نباید قابل ارسال باشد؛ در صورت رسیدن درخواست از مسیر غیر UI نیز باید پیش از ingestion رد شود.
- این سند قرارداد منطقی است و مجوز تغییر ORM، schema، migration یا مسیر persistence نیست.

## 2. فهرست انتخاب نوع ورودی

### 2.1 ورودی‌های CODAL

دو گزینهٔ مستقل و مشترک بین صنایع وجود دارد:

1. `MONTHLY_ACTIVITY` — گزارش فعالیت ماهانه.
2. `PERIODIC_FINANCIAL` — گزارش مالی دوره‌ای سال مالی، شامل گزارش‌های ۳، ۶، ۹ و ۱۲ماهه.

YTD، standalone-quarter، audited، unaudited، original و restated نوع ورودی مستقل نیستند؛ این‌ها ویژگی‌های زمانی یا نسخه‌ای داده/گزارش‌اند و باید از شواهد گزارش تفسیر شوند. نوع گزارش ۱۲ماهه از نظر ماهیت گزارش سالانه است، اما ReportType سوم ایجاد نمی‌کند.

فرمت ورودی صورت‌های مالی CODAL در V1، Excel معتبر است. PDF در دامنهٔ مسیر ورودی جاری نیست. فایل ناسازگار یا دارای ساختار/محتوای پشتیبانی‌نشده باید رد شود؛ تبدیل خودکار PDF یا دسته‌بندی مجدد انجام نمی‌شود.

### 2.2 ورودی‌های مستقل غیرصورت‌مالی

دامنه‌های منطقی مصوب عبارت‌اند از:

- `MARKET_DAILY` — دادهٔ روزانهٔ بازار؛
- `FX_RATE` — نرخ روزانه با انتخاب صریح نوع منبع، فقط FREE_MARKET یا EXCHANGE_CENTER؛
- `SHARE_COUNT_HISTORY` — تاریخچهٔ تعداد سهام، در صورت فعال‌شدن Feed/استاندارد معتبر؛
- `CORPORATE_ACTION` — رویداد شرکتی، در صورت فعال‌شدن Feed/استاندارد معتبر.

وجود دامنهٔ منطقی به معنی آماده‌بودن parser یا مجازبودن ingestion نیست. گزینهٔ UI فقط زمانی فعال می‌شود که source/feed profile و استاندارد نسخه‌دار آن دامنه تکمیل و فعال شده باشد. بر اساس شواهد فعلی، Feed profile بازار و Share/CorporateAction هنوز برای تصویب کافی نیست. قرارداد معنایی FX با تصمیم مالک 2026-11-19 روشن شده است، اما تقویم و provenance منبع و نمونهٔ FREE_MARKET برای فعال‌سازی Feedها همچنان باید تأیید شوند؛ بنابراین نباید گزینهٔ عملیاتیِ بدون استاندارد نمایش داده شود.

## 3. اطلاعات زمینه‌ای که کاربر باید مشخص کند

| نوع ورودی | انتخاب/اطلاعات الزامی کاربر | مواردی که سیستم باید resolve یا validate کند |
|---|---|---|
| CODAL Monthly Activity | شرکت، نوع گزارش، فایل Excel | company_id و صنعت یکتای شرکت؛ وجود استاندارد فعال همان شرکت/صنعت؛ تطبیق ساختار و Headerها؛ هویت گزارش و نسخه |
| CODAL Periodic Financial | شرکت، نوع گزارش، فایل Excel | company_id و صنعت یکتا؛ استاندارد فعال؛ ساختار جدول‌ها، HeaderPath، دوره و نسخه؛ عدم ابهام معنایی |
| Market Daily | شرکت، فایل تاریخچهٔ قیمت همان شرکت (بارگذاری مستقیم کاربر در اپلیکیشن)؛ Feed/قالب معتبر و فعال باید از قبل در سیستم تعریف شده باشد | تطبیق شرکت انتخاب‌شده با هویت/نماد فایل در صورت وجود، تقویم، schema ستون‌ها، واحد/scale و metadata زمانی طبق Feed profile |
| FX Rate | نوع نرخ (FREE_MARKET یا EXCHANGE_CENTER)، Feed/source profile فعال، فایل | هویت منبع، تاریخ جلالی، قالب عددی و واحد متناسب با نوع: EXCHANGE_CENTER=Rial/USD بدون تبدیل؛ FREE_MARKET=Toman/USD با تبدیل ×۱۰ به Rial/USD |
| Share Count History | شرکت، Feed/source profile فعال، فایل | تاریخ اثر/as-of، basis، واحد شمارش، publication/availability و revision |
| Corporate Action | شرکت، Feed/source profile فعال، فایل | نوع رویداد و معنای آن، شناسه/هویت رویداد، تاریخ‌های اعلام/تصویب/اثر، terms و revision |

Industry برای شرکت به‌صورت یک ویژگی یکتا و اجباری از Company master resolve می‌شود؛ کاربر نباید در هر بار بارگذاری بتواند صنعت شرکت را برای همان ingestion به‌دلخواه عوض کند. اگر شرکت یا صنعت نامعلوم/مبهم باشد، ابتدا باید Company master اصلاح شود و تا آن زمان ingestion متوقف است.

فیلدهای اختیاری UI فقط زمانی نمایش داده می‌شوند که Feed profile فعال آن‌ها را تعریف کرده باشد. این قرارداد اجازه نمی‌دهد UI برای پرکردن شکاف استاندارد، مقادیر پیش‌فرضی مانند واحد، scale، calendar، fiscal-year start یا publication time بسازد.

## 4. رفتار اعتبارسنجی و عدم انطباق

ترتیب منطقی:

1. دریافت نوع ورودی انتخاب‌شده و زمینهٔ لازم.
2. احراز وجود استاندارد/Feed profile فعال و نسخه‌دار برای همان نوع.
3. resolve کردن Company/Industry/Source؛ عدم resolve یکتا hard failure است.
4. اعتبارسنجی فرمت و ساختار فایل با همان استاندارد انتخاب‌شده.
5. اعتبارسنجی کامل محتوا، تاریخ، واحد، scale، temporal meaning، نسخه و logical identity طبق دامنه.
6. فقط پس از عبور کامل validation، ارسال یک Ingestion Unit به مرز persistence اتمیک.

رفتارهای الزامی:

- فایل با نوع انتخاب‌شده ناسازگار است: Reject؛ نوع دیگری به‌صورت خودکار پیشنهاد/اعمال نمی‌شود.
- استاندارد یا Feed profile موجود/فعال نیست: عدم امکان ارسال و پیام روشن به کاربر.
- شرکت/صنعت/منبع نامعلوم یا مبهم است: توقف؛ حدس یا مقدار پیش‌فرض ممنوع.
- Header، Metric، Dimension، period، unit یا معنای مقدار مبهم است: در مواردی که قرارداد همان دامنه اجازهٔ clarification می‌دهد، سؤال مشخص از کاربر و توقف کامل پردازش تا پاسخ؛ در غیر این صورت Reject.
- پاسخ دریافت نشود یا ابهام رفع نشود: کل گزارش/واحد ورودی Reject می‌شود.
- ثبت بخشی از گزارش مالی یا batch پس از خطای سخت مجاز نیست.
- Quarantine برای گزارش‌های مالی دوره‌ای طبق تصمیم مالک استفاده نمی‌شود.
- خطای validation نباید با Warning غیرمسدودکننده یا discard ضمنی پنهان شود؛ فقط موردی که استاندارد نسخه‌دار صریحاً out-of-scope کرده می‌تواند کنار گذاشته شود.

## 5. مرز مسئولیت UI و سیستم

**UI مسئول است برای:**
- نمایش فقط گزینه‌های ورودی که استاندارد فعال دارند؛
- دریافت نوع ورودی و اطلاعات زمینه‌ای لازم؛
- نمایش خطاها/ابهام‌های برگشتی و جلوگیری از ارسال مجدد بدون رفع موارد الزامی؛
- عدم ارائهٔ کنترل‌هایی که کاربر با آن‌ها بتواند قرارداد معنایی مصوب را دور بزند.

**سیستم مسئول است برای:**
- اعتبارسنجی مستقل تمام انتخاب‌ها و فایل، حتی اگر درخواست مستقیماً به API برسد؛
- resolve یکتای Company، Industry و Source؛
- اعمال نسخهٔ مشخص استاندارد/Feed profile؛
- عدم تشخیص عمومی یا تغییر خودکار نوع؛
- توقف fail-closed در ابهام و رد کامل واحد در hard failure؛
- حفظ atomicity و audit در لایهٔ ingestion.

UI مرجع نهایی اعتبارسنجی نیست و پنهان‌کردن گزینه یا disable کردن دکمه جایگزین validation سمت سرور نمی‌شود.

## 6. خطاها و پیام‌های قابل اقدام

پیام کاربر باید دست‌کم نوع مسئله و اقدام لازم را بیان کند، بدون نمایش stack trace یا اطلاعات داخلی:

- نوع ورودی انتخاب‌شده استاندارد فعال ندارد؛
- شرکت انتخاب‌شده صنعت معتبر/یکتا ندارد؛
- فایل با استاندارد نوع انتخاب‌شده منطبق نیست؛
- Feed profile یا منبع انتخاب‌شده ناشناخته/غیرفعال است؛
- تاریخ، واحد، scale یا زمان انتشار از منبع قابل اثبات نیست؛
- معنای Header/Metric/period مبهم است و نیاز به پاسخ دارد؛
- کل واحد ورودی رد شد و هیچ دادهٔ canonical از آن ثبت نشد.

## 9. اصلاحیهٔ FX — 2026-11-19

طبق تصمیم صریح مالک، واحد منبع برای دو نوع FX یکسان نیست: `EXCHANGE_CENTER` ورودی ریالی و بدون تبدیل دارد؛ `FREE_MARKET` ورودی تومانی دارد و برای canonical Rial/USD در ۱۰ ضرب می‌شود. برای فایل نمونهٔ مرکز مبادله، ستون «فروش (ریال)» تنها نرخ canonical است و ستون خرید ذخیره نمی‌شود. این تصمیم، نیاز به Feed profile واقعی، تقویم و provenance را حذف نمی‌کند. این اصلاحیه فقط مستندات را تغییر داد و هیچ کد یا داده‌ای را تغییر نداد.


## 10. تکمیل تصمیم مسیر دریافت MarketDaily — 2026-11-19

مالک تأیید کرد که کاربر فایل تاریخچهٔ قیمت را از طریق اپلیکیشن بارگذاری می‌کند و برای هر شرکت فایل همان شرکت دریافت می‌شود؛ مشابه مسیر بارگذاری سایر گزارش‌های شرکت. بنابراین برای دریافت MarketDaily در V1 اتصال مستقیم به API یا وب‌سایت بیرونی لازم نیست. این تصمیم فقط کانال دریافت را مشخص می‌کند و جایگزین Feed profile معتبر نیست: قالب تاریخ/تقویم، ستون‌ها، واحد و scale، تطبیق هویت شرکت، provenance دادهٔ داخل فایل و رفتار اصلاحیه باید همچنان پیش از فعال‌سازی استاندارد شوند. منبع اولیه‌ای که کاربر فایل را از آن تهیه می‌کند، از این تصمیم معلوم نمی‌شود و نباید حدس زده شود. این اصلاحیه فقط مستندات را تغییر داد؛ هیچ کد، UI، API، ORM، schema، migration یا داده‌ای تغییر نکرد/اجرا نشد.


## 11. تکمیل معنای فیلدهای MarketDaily برای Feed نمونه — 2026-11-19

برای فایل نمونهٔ `saman_price_history.csv`، مالک واحد قیمت را ریال به‌ازای هر سهم و واحد حجم را تعداد سهم معامله‌شده تأیید کرد. در نتیجه اطلاعات/اعتبارسنجی MarketDaily برای همین Feed باید این تمایز را رعایت کند:

- `Close` → `market_price` با واحد Rial/share و بدون تبدیل ×۱۰؛
- `Volume` → تعداد سهام معامله‌شده با واحد share؛
- `No` → تعداد دفعات معامله با واحد trade؛
- `Value` → ارزش کل معاملات با واحد Rial؛ در V1 دریافت/ذخیره نمی‌شود.

این تصمیم معنایی، جایگزین Feed profile نسخه‌دار نیست و به قالب شرکت‌های دیگر تعمیم داده نمی‌شود. تقویم/قالب تاریخ، منبع اولیه، provenance و revision همچنان باید در Feed profile مشخص شوند. هیچ گزینهٔ MarketDaily تا فعال‌شدن Feed profile معتبر قابل ارسال نیست. فقط مستندات تغییر کردند؛ هیچ UI، کد، API، ORM، schema، migration یا داده‌ای تغییر نکرد/اجرا نشد.
